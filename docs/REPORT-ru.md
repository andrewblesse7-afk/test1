# DormFlow — отчёт по проекту

**Портал для студенческого общежития**

Студенты подают заявки на ремонт и бронируют общие помещения (прачечную,
учебную комнату, спортзал). Администратор обрабатывает заявки, управляет
помещениями и публикует объявления.

Я выбрал эту тему, потому что тут есть сразу два рабочих процесса из задания:
заявка проходит через несколько статусов, а бронь не должна накладываться на
чужую. Обе проверки я сделал на сервере, а не в браузере.

## 1. Фронтенд

**Структура.** Восемь обычных HTML-страниц в папке `public/`. Express отдаёт их
одной строкой: `app.use(express.static("public"))`. У каждой страницы свой файл
со скриптом, плюс общий `auth.js` для работы с токеном.

Фреймворк не использовал: в задании нужны HTML, CSS и JavaScript, и на обычном
JS я понимаю каждую строку своего кода.

**Стили.** Все стили в одном файле `style.css`. Цвета вынес в CSS-переменные,
поэтому тему можно поменять в одном месте. Вёрстка mobile-first: сначала
описан узкий экран, а один медиазапрос на 640px делает раскладку для широких —
например, навигация из столбика превращается в строку.

> 📷 **СКРИНШОТ 2** → `02-mobile.png` — та же страница на узком экране (F12 →
> режим телефона). Видно, что вёрстка подстроилась.

**Что делает JavaScript:**
- После входа сохраняет токен в `localStorage` и добавляет его заголовком
  `Authorization` к каждому запросу.
- Если токена нет или сервер ответил `401` — отправляет на страницу входа.
- Списки строит через `createElement` и `textContent`, а не `innerHTML`. Так
  текст, который написал студент, показывается как текст и не выполняется как
  код.
- В форме брони склеивает поля даты и времени в настоящую дату и отправляет её
  в UTC, чтобы время не сдвинулось.

> 📷 **СКРИНШОТ 3** → `03-requests.png` — страница заявок: форма и список.

## 2. База данных

MongoDB и Mongoose, пять моделей:

| Модель | Поля |
|---|---|
| `User` | имя, email (уникальный), хеш пароля, комната, роль |
| `MaintenanceRequest` | автор → User, комната, категория, описание, приоритет, статус, история статусов |
| `Facility` | название, место, вместимость, длина слота, цена слота |
| `Booking` | пользователь → User, помещение → Facility, начало, конец, статус |
| `Announcement` | заголовок, текст, категория, автор → User |

Везде стоит `{ timestamps: true }` — даты создания и изменения добавляются сами.
Для полей с готовым набором значений (статус, категория, роль) использую `enum`,
чтобы в базу не попало что-то лишнее.

**Решения, которые считаю важными:**
- Пароль в базе не хранится, только bcrypt-хеш. У поля стоит `select: false`,
  поэтому обычные запросы его даже не загружают и он не может попасть в ответ.
- Автор заявки — ссылка на пользователя, а не его имя строкой. Сначала я сделал
  строкой, но по имени нельзя надёжно проверить, чья это заявка, и после
  появления модели `User` я это переделал.
- История статусов лежит массивом внутри самой заявки. Для проекта такого
  размера это проще, чем отдельная коллекция.
- Время брони — настоящие даты `Date`, а не строки. Строки неудобно сравнивать,
  и на них ломаются часовые пояса.

**Индексы.** Без индекса MongoDB читает всю коллекцию, а с индексом сразу
находит нужные записи. Сделал индексы для списка заявок админа, для «моих
заявок» и «моих броней». Ещё один, самый важный, описан ниже.

> 📷 **СКРИНШОТ 5** → `05-database.png` — заявка в базе с заполненной историей
> статусов (MongoDB Compass или `mongosh`).

## 3. Сервер: контроллеры, маршруты, API

**Структура.** Код разделён на папки: `routes` (какой адрес какую функцию
вызывает), `middleware` (проверки до контроллера), `controllers` (логика и
работа с базой), `models` (как хранятся данные). Файл `server.js` только
связывает всё вместе.

**Три middleware:**
- `auth.js` — проверяет токен и находит пользователя. Нет токена → `401`.
- `requireAdmin.js` — роль не админ → `403`. Разница простая: `401` значит «я не
  знаю, кто ты», `403` — «знаю, но тебе сюда нельзя».
- `errorHandler.js` — в одном месте превращает ошибки в нужные коды: неверный id
  → `400`, ошибка проверки данных → `400`, дубликат → `409`.

**Права доступа.** Студент видит только свои записи, и это сделано прямо в
запросе к базе, а не скрытием кнопок на странице:
```js
const filter = req.user.role === "admin" ? {} : { resident: req.user._id };
```
Фильтры из поиска добавляются к этому же объекту, поэтому ограничение не
теряется. Чужую заявку нельзя открыть даже прямым запросом к API.

**Статусы заявки.** Статус меняется только отдельным адресом
`PATCH /api/requests/:id/status`. Сервер сверяется с таблицей переходов:
```
Submitted   → Reviewed, Rejected, Cancelled
Reviewed    → In Progress, Rejected
In Progress → Completed
Completed, Rejected, Cancelled → дальше никуда
```
Если перехода нет в таблице, сервер отвечает `409` и статус не меняется. Каждое
изменение дописывает запись в историю через `$push` — эта операция только
добавляет, поэтому старые записи не потеряются.

> 📷 **СКРИНШОТ 6** → `06-status-409.png` — попытка вернуть завершённую заявку в
> начало: ответ `409`.

**Бронирование.** Две брони пересекаются, если новая начинается раньше, чем
заканчивается старая, и заканчивается позже, чем старая началась. Но проверки в
коде мало: два запроса могут пройти её одновременно. Поэтому главная защита —
уникальный индекс в самой базе на помещение и время начала. Он учитывает только
активные брони, поэтому после отмены слот снова свободен. Если база отклоняет
запись, сервер отвечает `409`.

> 📷 **СКРИНШОТ 7** → `07-booking-409.png` — попытка занять уже забронированный
> слот.

**API — 23 адреса:** `/api/auth` (3), `/api/requests` (6), `/api/facilities` (5),
`/api/bookings` (4), `/api/announcements` (5). Список заявок принимает фильтры
по статусу, категории, приоритету, комнате и поиск по тексту.

Коды ответов: `200`, `201`, `400`, `401`, `403`, `404`, `409`.

## 4. Docker и запуск

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
USER node
CMD ["node", "server.js"]
```

Сначала копирую только `package.json`, а потом уже код. Docker запоминает слои,
поэтому установка пакетов повторяется только когда меняются зависимости, а не
после каждой правки в HTML. Файл `.dockerignore` не пускает в образ `.env` —
секреты передаются при запуске, а не лежат внутри образа.

**Как запустить:**
```bash
npm install
cp .env.example .env      # вписать MONGODB_URI и JWT_SECRET
npm run seed              # демо-данные
npm start                 # http://localhost:3000
```
Через Docker: `docker build -t dormflow .`, потом
`docker run -p 3000:3000 --env-file .env dormflow`.

`anna@dormflow.test` — студент.

## Что проверял и чего не хватает

Проверял вручную через `curl` и PowerShell: без токена приходит `401`, студенту
на админском адресе — `403`, неправильный переход статуса — `409`, повторная
бронь того же слота — `409`.

Чего не хватает: проект учебный и не готов к реальной работе; автотестов нет;
образ Docker я написал, но собрать его пока не проверял; токен живёт семь дней
и отозвать его нельзя; оплата не сделана, хотя поле цены у помещений есть;
в дашборде нет постраничной навигации.

Что можно добавить дальше: имитацию оплаты, загрузку фото к заявкам,
автоматические тесты и уведомления при смене статуса.
