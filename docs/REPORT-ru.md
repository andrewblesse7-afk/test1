# DormFlow — отчёт по проекту

**Портал управления студенческим общежитием**

Студенты сообщают о поломках в комнатах и бронируют общие помещения.
Администратор обрабатывает заявки, управляет помещениями и публикует
объявления. Тему выбрал потому, что она требует обоих рабочих процессов из
задания: заявка проходит через несколько состояний, а бронирование не должно
накладываться на чужое. Оба правила проверяются на сервере.

## 1. Фронтенд: структура, стили, ключевой JavaScript

**Структура.** Восемь статических HTML-страниц в `public/`, Express отдаёт их
строкой `app.use(express.static("public"))`. У каждой страницы свой скрипт
(`requests.js`, `bookings.js`, `activity.js`, `admin.js`, `announcements.js`,
`login.js`, `register.js`) плюс общий `auth.js`. Фреймворк не использовал:
задание требует HTML, CSS и JavaScript, а на обычном JS я могу объяснить каждую
строку.

**Стили.** Один файл `public/css/style.css`. Цвета заданы CSS-переменными в
`:root`, поэтому тема меняется в одном месте. Вёрстка mobile-first: базовые
правила описывают узкий экран, один медиазапрос на `640px` улучшает раскладку
на широких (навигация из столбика становится строкой). Карточки и бейджи
статусов — общие классы для всех страниц.

> 📷 **СКРИНШОТ 2** → `02-mobile.png` — та же страница на узком экране
> (F12 → режим телефона, 390px). Видно, что навигация перестроилась в столбик.

**Ключевой JavaScript:**
- `auth.js` хранит токен в `localStorage`, собирает заголовок
  `Authorization: Bearer <токен>` и показывает имя вошедшего в навигации.
  Ссылка Admin добавляется только при роли `admin`.
- Каждая защищённая страница начинается с проверки: нет токена — уход на вход.
  Ответ `401` — токен удаляется, пользователь снова на входе.
- Списки строятся через `createElement` и `textContent`, а не `innerHTML`: текст,
  введённый студентом, показывается как текст и никогда не выполняется.
- В форме брони поля даты и времени склеиваются в настоящую дату и уходят в UTC
  через `toISOString()`, поэтому время не сдвигается.

> цветными бейджами статусов (после `npm run seed`, вход `anna@dormflow.test`).

## 2. Схема базы данных и модели

MongoDB + Mongoose, пять моделей:

| Модель | Основные поля |
|---|---|
| `User` | `name`, `email` (уникальный), `passwordHash`, `roomNumber`, `role` |
| `MaintenanceRequest` | `resident` → User, `roomNumber`, `category`, `description`, `priority`, `status`, `statusHistory[]` |
| `Facility` | `name`, `location`, `capacity`, `available`, `slotMinutes`, `pricePerSlot` |
| `Booking` | `userId` → User, `facilityId` → Facility, `startAt`, `endAt`, `status` |
| `Announcement` | `title`, `content`, `category`, `createdBy` → User |

Везде `{ timestamps: true }` добавляет `createdAt` и `updatedAt`. Поля с
фиксированным набором значений описаны через `enum`.

**Решения, которые считаю важными:**
- **Пароль не хранится** — только bcrypt-хеш, поле с `select: false`, поэтому
  обычные запросы его не загружают и он не попадёт в ответ API.
- **Владелец — ссылка, а не имя.** Сначала `resident` был строкой с именем, но
  по имени нельзя надёжно проверить владельца, и после появления модели
  пользователя поле стало `ObjectId`.
- **История статусов вложена в заявку** массивом `statusHistory`, а не отдельной
  коллекцией: для проекта такого размера проще, история едет вместе с заявкой.
- **Даты — настоящие `Date`**, а не строки: строки неудобно сравнивать и на них
  ломаются часовые пояса. Прошедшие брони находятся условием `endAt < now`.

**Индексы.** Без индекса MongoDB читает всю коллекцию, с индексом идёт сразу к
нужным документам. Поле для фильтра стоит первым, для сортировки — вторым:
`{status, createdAt}` и `{resident, createdAt}` для заявок, `{userId, startAt}`
для броней, уникальный email у пользователя. Пятый индекс — в разделе 3.

> 📷 **СКРИНШОТ 5** → `05-database.png` — документ заявки в MongoDB Compass или
> `mongosh` с заполненным `statusHistory`. Показывает, что история реально
> хранится в базе.

## 3. Контроллеры, маршруты и эндпоинты

**Структура.** Четыре слоя: `routes/` (какой URL какой функции),
`middleware/` (проверки до контроллера), `controllers/` (логика и обращения к
базе), `models/` (хранение). `server.js` только связывает всё вместе.

**Три middleware:**
- `auth.js` — проверяет подпись токена, находит пользователя, кладёт в
  `req.user`. Без токена → `401`.
- `requireAdmin.js` — роль не `admin` → `403`. Разница важна: `401` — «не знаю,
  кто ты», `403` — «знаю, но нельзя».
- `errorHandler.js` — в одном месте превращает ошибки в коды: неверный id →
  `400`, ошибка валидации → `400`, дубликат → `409`, остальное → `500` с
  подробностями только в логе.

**Контроль доступа** сделан в запросе к базе, а не скрытием элементов:
```js
const filter = req.user.role === "admin" ? {} : { resident: req.user._id };
```
Фильтры из адресной строки добавляются к этому объекту, поэтому ограничение по
владельцу не теряется при поиске. Владелец новой записи берётся из токена, а не
из тела запроса.

**Рабочий процесс заявки.** Статус меняется только своим эндпоинтом
`PATCH /api/requests/:id/status` по таблице переходов на сервере:
```js
Submitted → Reviewed, Rejected, Cancelled
Reviewed → In Progress, Rejected
In Progress → Completed
Completed, Rejected, Cancelled → (конечные)
```
Переход не из таблицы → `409`, заявка сохраняет прежний статус. Каждое
изменение дописывает запись в историю операцией `$push` — она только добавляет,
поэтому старые записи не теряются и их нельзя отредактировать.

> 📷 **СКРИНШОТ 6** → `06-status-409.png` — попытка перевести завершённую заявку
> обратно в `Submitted` отклоняется с кодом `409`.

**Конфликты бронирования.** Пересечение ищется условием
`startAt < новыйКонец && endAt > новоеНачало` среди активных броней. Проверки в
коде мало: два запроса могут пройти её одновременно. Настоящая защита —
уникальный индекс `{facilityId, startAt}` с `partialFilterExpression: {status:
"Active"}`. Отменённая бронь выпадает из индекса, и слот снова свободен. Ошибку
базы `11000` контроллер превращает в `409`.

> 📷 **СКРИНШОТ 7** → `07-booking-409.png` — попытка занять забронированный слот:
> «This time slot is already booked».

**Эндпоинты — 23 в пяти группах:** `/api/auth` (3), `/api/requests` (6, включая
смену статуса), `/api/facilities` (5), `/api/bookings` (4),
`/api/announcements` (5). Список заявок принимает фильтры
`?status=&category=&priority=&roomNumber=&q=`, где `q` ищет по описанию и номеру
комнаты (текст экранируется перед подстановкой в регулярное выражение).

Коды: `200`, `201`, `400`, `401`, `403`, `404`, `409`.

## 4. Развёртывание и запуск

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
USER node
CMD ["node", "server.js"]
```

Манифесты копируются раньше исходников намеренно: Docker кэширует слои, и
`npm ci` выполняется заново только при смене зависимостей, а не после каждой
правки в HTML. `--omit=dev` пропускает ненужные для работы пакеты, контейнер
запускается от непривилегированного пользователя.

`.dockerignore` не пускает в образ `node_modules`, `.git` и `.env` — секреты
передаются при запуске, а не «запекаются» в образ. `node_modules` исключены ещё
и потому, что `bcrypt` компилируется под конкретную ОС, и сборка с Windows не
запустится в Linux-контейнере.

**Запуск:**
```bash
npm install
cp .env.example .env      # вписать MONGODB_URI и JWT_SECRET
npm run seed              # демо-данные (сначала очищает базу)
npm start                 # http://localhost:3000
```
Через Docker: `docker build -t dormflow .`, затем
`docker run -p 3000:3000 --env-file .env dormflow`. Если MongoDB на самом
компьютере, в строке подключения нужен `host.docker.internal`, а не `localhost`.

## Проверка и ограничения

API проверялся вручную через `curl` и PowerShell: запрос без токена → `401`,
студент на административном маршруте → `403`, недопустимый переход → `409`,
повторное бронирование слота → `409`.

Ограничения: проект учебный и не готов к промышленной эксплуатации;
автоматических тестов нет; образ Docker написан по стандартным шагам и
приложение проверено на работу только с production-зависимостями, но сама
сборка ещё не выполнялась; токен действует семь дней и не отзывается досрочно;
поле `pricePerSlot` есть, но оплата не реализована; в дашборде нет постраничной
навигации, хотя API поддерживает `page` и `limit`.

Возможные улучшения: имитация оплаты, загрузка фотографий к заявкам,
автоматические тесты, уведомления при смене статуса.
