# DormFlow — отчёт по проекту

**Портал управления студенческим общежитием**

DormFlow — веб-приложение для студенческого общежития. Студенты сообщают о
поломках в комнатах и бронируют общие помещения, например прачечную.
Администратор обрабатывает заявки, управляет помещениями и публикует
объявления.

Я выбрал эту тему, потому что она требует обоих видов рабочих процессов,
которые нужны по заданию: заявка проходит через несколько состояний, а
бронирование не должно накладываться на чужое. Оба правила приходится проверять
на сервере, и именно это сделало проект интересным.

> **📷 СКРИНШОТ 1 — `docs/screenshots/01-landing.png`**
> Главная страница целиком на широком экране: шапка с навигацией, заголовок,

## 1. Структура фронтенда, подход к стилям и ключевой JavaScript

### Структура

Фронтенд — это восемь статических HTML-страниц в папке `public/`. Express
отдаёт их одной строкой `app.use(express.static("public"))`. У каждой страницы
свой файл со скриптом плюс один общий:

| Страница | Скрипт | Назначение |
|---|---|---|
| `index.html` | — | главная страница |
| `login.html` / `register.html` | `login.js` / `register.js` | вход и регистрация |
| `requests.html` | `requests.js` | создание и список заявок |
| `bookings.html` | `bookings.js` | помещения, форма брони, мои брони |
| `activity.html` | `activity.js` | заявки, брони и история статусов |
| `announcements.html` | `announcements.js` | объявления, форма для админа |
| `admin.html` | `admin.js` | дашборд со счётчиками и фильтрами |
| все страницы | `auth.js` | работа с токеном и навигация |

Фронтенд-фреймворк я не использовал. Задание требует HTML, CSS и JavaScript, а
обычный JavaScript позволил мне понимать и объяснить каждую строку проекта.

### Подход к стилям

Все стили лежат в одном файле `public/css/style.css`. Цвета заданы один раз
как CSS-переменные в `:root`, поэтому тему можно поменять в одном месте.

Вёрстка построена по принципу mobile-first: основные правила описывают узкий
экран, а один медиазапрос на `640px` улучшает раскладку на широких. Например,
навигация по умолчанию идёт столбиком, а начиная с этой ширины становится
горизонтальной строкой. Карточки, бейджи статусов и стили форм — общие классы,
которые переиспользуются на всех страницах, поэтому файл остался небольшим.

### Ключевой JavaScript

**Работа с токеном (`auth.js`).** После входа токен сохраняется в
`localStorage`, поэтому он переживает перезагрузку страницы. Функция
`authHeaders()` собирает заголовок `Authorization: Bearer <токен>`, который
нужен каждому защищённому запросу. Функция `showCurrentUser()` обращается к
`/api/auth/me`, заменяет ссылки Login и Register на имя пользователя и ссылку
Logout, а ссылку Admin добавляет только если роль — `admin`.

**Защита страницы.** Каждая защищённая страница начинается с одной и той же
проверки: если токена нет, браузер уходит на страницу входа. Если сервер
ответил `401`, токен удаляется и пользователь тоже отправляется на вход.

**Отрисовка списков.** Списки собираются через `document.createElement` и
`textContent`, а не через `innerHTML`. Это важно для безопасности: студент может
вписать в описание заявки HTML-теги, и при `textContent` они всегда
показываются как обычный текст и никогда не выполняются.

**Даты в форме бронирования.** В форме отдельные поля для даты и времени, но
база хранит настоящие даты. Скрипт склеивает их и переводит в нужный формат:

```js
const startAt = new Date(`${date}T${bookingForm.startTime.value}`);
// ...
body: JSON.stringify({ startAt: startAt.toISOString(), ... })
```

Браузер читает введённое значение как местное время, а `toISOString()`
отправляет его в UTC, поэтому при сохранении время не сдвигается.

## 2. Схема базы данных и модели

Проект использует MongoDB и Mongoose. Всего пять моделей.

| Модель | Основные поля |
|---|---|
| `User` | `name`, `email` (уникальный), `passwordHash`, `roomNumber`, `role` |
| `MaintenanceRequest` | `resident` → User, `roomNumber`, `category`, `description`, `priority`, `status`, `adminComment`, `statusHistory[]` |
| `Facility` | `name`, `description`, `location`, `capacity`, `available`, `slotMinutes`, `pricePerSlot` |
| `Booking` | `userId` → User, `facilityId` → Facility, `startAt`, `endAt`, `status` |
| `Announcement` | `title`, `content`, `category`, `createdBy` → User |

Во всех моделях указано `{ timestamps: true }` — Mongoose сам добавляет
`createdAt` и `updatedAt`. Поля с фиксированным набором значений (`status`,
`category`, `role`) описаны через `enum`, поэтому база не примет значение не из
списка.

### Проектные решения

**Пароль не хранится.** В базу попадает только bcrypt-хеш. Поле объявлено с
`select: false`, то есть обычные запросы его вообще не загружают, и он не может
случайно попасть в ответ API. Контроллер входа запрашивает его явно через
`.select("+passwordHash")`.

**Владелец — ссылка, а не имя.** Поля `resident` и `userId` — это `ObjectId`
со ссылкой на `User`. В первой версии `resident` был обычной строкой с именем
студента, но по имени нельзя надёжно проверить владельца, поэтому после
появления модели пользователя поле было заменено.

**История статусов вложена в заявку.** `statusHistory` — это массив внутри
документа заявки, а не отдельная коллекция. Каждая запись хранит `from`, `to`,
`changedBy`, `comment` и `changedAt`. Для проекта такого размера вложенный
массив проще: история всегда едет вместе с заявкой и не требует лишнего запроса.

**Бронирования хранят настоящие даты.** `startAt` и `endAt` — поля типа `Date`.
Я не стал использовать отдельные текстовые поля для даты и времени, потому что
текст неудобно сравнивать и на нём ломаются часовые пояса. Прошедшие брони
находятся условием `endAt < now`, поэтому отдельный статус для них не нужен.

### Индексы

```js
// User.js — объявлен прямо на поле
email: { type: String, required: true, unique: true, lowercase: true }

// MaintenanceRequest.js
maintenanceRequestSchema.index({ status: 1, createdAt: -1 });
maintenanceRequestSchema.index({ resident: 1, createdAt: -1 });

// Booking.js
bookingSchema.index({ userId: 1, startAt: -1 });
bookingSchema.index(
  { facilityId: 1, startAt: 1 },
  { unique: true, partialFilterExpression: { status: "Active" } }
);
```

Без индекса MongoDB читает всю коллекцию, с индексом — идёт сразу к нужным
документам. В каждом индексе поле для фильтрации стоит первым, а поле для
сортировки вторым, поэтому один индекс обслуживает и поиск, и упорядочивание.

Последний индекс — самый важный, он объясняется в разделе 3.

## 3. Контроллеры, маршруты и эндпоинты

### Структура

Сервер разделён на четыре слоя:

```
routes/       какой URL и метод какой функции принадлежит
middleware/   проверки, которые выполняются до контроллера
controllers/  логика и обращения к базе
models/       как данные хранятся
```

`server.js` только связывает всё вместе: разбирает JSON, подключается к
MongoDB, отдаёт статические файлы, монтирует пять роутеров и заканчивается
обработчиком `404` и обработчиком ошибок.

Middleware три:

- **`auth.js`** читает заголовок `Authorization`, проверяет подпись токена
  секретом из `.env`, находит пользователя в базе и кладёт его в `req.user`.
  Без действительного токена ответ — `401`.
- **`requireAdmin.js`** выполняется после него и отвечает `403`, если роль не
  `admin`. Разница важна: `401` значит «я не знаю, кто ты», `403` — «я знаю, кто
  ты, но сюда нельзя».
- **`errorHandler.js`** превращает ошибки в правильные коды в одном месте:
  неверный id → `400`, ошибка валидации → `400` с сообщением от модели,
  дубликат ключа → `409`, всё неожиданное остаётся `500`, а подробности
  пишутся только в лог сервера.

Маршрут защищается просто — middleware ставится перед контроллером:

```js
router.post("/", requireAdmin, createFacility);
```

### Контроль доступа

Студент не должен видеть чужие данные. Это сделано **в запросе к базе внутри
контроллера**, а не скрытием элементов на странице:

```js
const filter = req.user.role === "admin" ? {} : { resident: req.user._id };
```

Фильтры из адресной строки **добавляются** к этому объекту, поэтому ограничение
по владельцу не теряется, даже когда студент пользуется поиском. Чужую заявку
нельзя получить даже прямым обращением к API — ответ будет `403`.

Владелец новой записи всегда берётся из токена (`resident: req.user._id`), а не
из тела запроса, поэтому создать заявку от чужого имени невозможно.

### Рабочий процесс заявки

Обычный `PATCH /api/requests/:id` статус не меняет. У статуса свой эндпоинт
`PATCH /api/requests/:id/status`, и решение принимает сервер по таблице
переходов:

```js
const allowedTransitions = {
  Submitted:     ["Reviewed", "Rejected", "Cancelled"],
  Reviewed:      ["In Progress", "Rejected"],
  "In Progress": ["Completed"],
  Completed: [], Rejected: [], Cancelled: [],
};
```

Пустой список означает конечный статус, поэтому завершённая заявка никогда не
вернётся в начало. Переход, которого нет в таблице, получает `409`, и заявка
сохраняет прежний статус. Менять статус может только администратор; студент
может лишь отменить свою заявку, пока она в статусе `Submitted`.

Каждое успешное изменение дописывает одну запись в историю той же операцией с
базой:

```js
{ $set: updates, $push: { statusHistory: historyEntry } }
```

`$push` только добавляет, поэтому старые записи не могут потеряться, и ни один
эндпоинт не умеет их редактировать или удалять.

> **📷 СКРИНШОТ 7 — `docs/screenshots/07-status-409.png`**
> Терминал: попытка недопустимого перехода (например из `Completed` в
> `Submitted`) отклоняется с кодом `409` и понятным сообщением.
> Как снять: войти администратором, взять id завершённой заявки и выполнить

>   -Body '{"status":"Submitted"}'
> ```
> В ответе должно быть `409` и текст `Cannot change status from "Completed" to "Submitted"`.

### Конфликты бронирования

Два интервала пересекаются, когда новый начинается раньше, чем заканчивается
старый, и заканчивается позже, чем старый начинается:

```js
startAt: { $lt: end }, endAt: { $gt: start }, status: "Active"
```

Проверки в коде недостаточно, потому что два запроса могут пройти её
одновременно. Настоящая защита — уникальный индекс по `facilityId` и `startAt`.
Его `partialFilterExpression` учитывает только активные брони, поэтому
отменённая бронь выпадает из индекса и слот снова становится свободным. Когда
база отклоняет вставку с ошибкой `11000`, контроллер отвечает `409`, а не `500`.
Отмена поэтому только меняет статус и сохраняет запись — так остаётся полная
история бронирований.

### Эндпоинты

Всего 23 эндпоинта в пяти группах:

| Группа | Эндпоинты |
|---|---|
| `/api/auth` | регистрация, вход, текущий пользователь |
| `/api/requests` | список, создание, чтение, изменение, удаление, смена статуса |
| `/api/facilities` | список, чтение, создание, изменение, удаление |
| `/api/bookings` | список, создание, чтение, отмена |
| `/api/announcements` | список, чтение, создание, изменение, удаление |

Список заявок принимает
`?status=&category=&priority=&roomNumber=&q=&page=&limit=`, где `q` ищет по
описанию и номеру комнаты. Текст поиска экранируется перед подстановкой в
регулярное выражение, поэтому спецсимвол не может изменить запрос.

Коды ответов: `200` успех, `201` создано, `400` неверные данные, `401` нет или
неверный токен, `403` доступ запрещён, `404` не найдено, `409` конфликт.

## 4. Конфигурация развёртывания и инструкция по запуску

### Dockerfile

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
USER node
CMD ["node", "server.js"]
```

Манифесты копируются раньше исходного кода намеренно. Docker кэширует каждый
слой, поэтому `npm ci` выполняется заново только при изменении зависимостей, а
не после каждой правки в HTML-файле. `npm ci` ставит точные версии из
`package-lock.json`, а `--omit=dev` пропускает пакеты, не нужные для работы
сервера. Контейнер запускается от непривилегированного пользователя `node`.

Файл `.dockerignore` не пускает в образ `node_modules`, `.git` и, что особенно
важно, `.env`. Секреты передаются при запуске, поэтому они не «запекаются» в файл,
который можно скопировать куда-то ещё. Исключение `node_modules` важно ещё и
потому, что `bcrypt` компилируется под конкретную операционную систему, и копия,
собранная на Windows, не запустится внутри Linux-контейнера.

### Инструкция по запуску

```bash
git clone <ссылка-на-репозиторий>
cd dormflow
npm install
cp .env.example .env      # затем вписать MONGODB_URI и JWT_SECRET
npm run seed              # демонстрационные данные (сначала очищает базу)
npm start                 # http://localhost:3000
```

Через Docker:

```bash
docker build -t dormflow .
docker run -p 3000:3000 --env-file .env dormflow
```

Если MongoDB запущена на самом компьютере, контейнер не достучится до неё через
`localhost`, потому что внутри контейнера `localhost` — это он сам. В строке
подключения нужно использовать `host.docker.internal`.

Демонстрационные аккаунты, которые создаёт `npm run seed`, используют пароль
`password123`: `admin@dormflow.test` — администратор, а `anna@dormflow.test`,
`bob@dormflow.test` и `clara@dormflow.test` — студенты.

## Проверка и ограничения

API проверялся вручную запросами через `curl` и PowerShell — проверялись и
успешные ответы, и коды ошибок: запрос без токена возвращает `401`, обращение
студента к административному маршруту — `403`, недопустимый переход статуса —
`409`, повторное бронирование того же слота — `409`.

Известные ограничения:

- Проект учебный и не готов к промышленной эксплуатации.
- Автоматических тестов нет, всё проверялось вручную.
- Образ Docker написан по стандартным шагам, и приложение проверено на работу
  только с production-зависимостями, но сама сборка образа ещё не выполнялась.
