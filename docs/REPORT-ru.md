# DormFlow — отчёт по проекту

**Портал для студенческого общежития.** Студенты подают заявки на ремонт и
бронируют общие помещения, администратор обрабатывает заявки и публикует
объявления. Выбрал эту тему, потому что тут два рабочих процесса из задания:
заявка проходит через статусы, а бронь не должна накладываться на чужую. Обе
проверки сделал на сервере, а не в браузере.

> 📷 **СКРИНШОТ 1** → `01-landing.png` — главная страница.

## 1. Фронтенд

Восемь обычных HTML-страниц в папке `public/`, Express отдаёт их строкой
`app.use(express.static("public"))`. У каждой страницы свой скрипт плюс общий
`auth.js`. Фреймворк не использовал: в задании нужны HTML, CSS и JavaScript, и
на обычном JS я понимаю каждую строку своего кода.

Стили в одном файле, цвета вынес в CSS-переменные. Вёрстка mobile-first:
сначала описан узкий экран, один медиазапрос на 640px делает раскладку для
широких.

> 📷 **СКРИНШОТ 2** → `02-mobile.png` — та же страница на узком экране.

Что делает JavaScript:
- хранит токен в `localStorage` и добавляет его заголовком к каждому запросу;
- если токена нет или пришёл `401` — отправляет на страницу входа;
- строит списки через `textContent`, а не `innerHTML`, чтобы текст студента
  показывался как текст и не выполнялся как код.

> 📷 **СКРИНШОТ 3** → `03-requests.png` — страница заявок: форма и список.

## 2. База данных

MongoDB и Mongoose, пять моделей:

| Модель | Поля |
|---|---|
| `User` | имя, email (уникальный), хеш пароля, комната, роль |
| `MaintenanceRequest` | автор → User, комната, категория, описание, приоритет, статус, история статусов |
| `Facility` | название, место, вместимость, длина слота, цена слота |
| `Booking` | пользователь → User, помещение → Facility, начало, конец, статус |
| `Announcement` | заголовок, текст, категория, автор → User |

Даты создания добавляются сами через `{ timestamps: true }`, а для полей с
готовым набором значений использую `enum`, чтобы в базу не попало лишнее.

Важные решения:
- **Пароль не хранится**, только bcrypt-хеш, и у поля стоит `select: false` —
  обычные запросы его не загружают, поэтому он не может попасть в ответ.
- **Автор заявки — ссылка на пользователя**, а не имя строкой. Сначала сделал
  строкой, но по имени нельзя проверить, чья это заявка, и потом переделал.
- **История статусов** лежит массивом внутри самой заявки — так проще, чем
  отдельная коллекция.
- **Время брони — настоящие `Date`**, а не строки: строки неудобно сравнивать и
  на них ломаются часовые пояса.

Индексы сделал для списка заявок админа, «моих заявок» и «моих броней»: без
индекса база читает всю коллекцию, с индексом сразу находит нужное.

## 3. Сервер

Код разделён на папки: `routes` (какой адрес какую функцию вызывает),
`middleware` (проверки до контроллера), `controllers` (логика и работа с базой),
`models`. Файл `server.js` только связывает всё вместе.

Три middleware: `auth.js` проверяет токен (нет токена → `401`),
`requireAdmin.js` проверяет роль (не админ → `403`), `errorHandler.js` в одном
месте превращает ошибки в нужные коды.

**Права доступа.** Студент видит только свои записи, и это сделано в запросе к
базе, а не скрытием кнопок:
```js
const filter = req.user.role === "admin" ? {} : { resident: req.user._id };
```
Фильтры поиска добавляются к этому же объекту, поэтому ограничение не теряется,
и чужую заявку нельзя открыть даже прямым запросом к API.

**Статусы заявки.** Меняются только отдельным адресом
`PATCH /api/requests/:id/status`, сервер сверяется с таблицей переходов:
```
Submitted   → Reviewed, Rejected, Cancelled
Reviewed    → In Progress, Rejected
In Progress → Completed
Completed, Rejected, Cancelled → дальше никуда
```
Переход не из таблицы → `409`, статус не меняется. Каждое изменение дописывает
запись в историю через `$push`: эта операция только добавляет, поэтому старые
записи не теряются.

> 📷 **СКРИНШОТ 6** → `06-status-409.png` — попытка вернуть завершённую заявку в
> начало: `409`.

**Бронирование.** Брони пересекаются, если новая начинается раньше, чем
заканчивается старая, и заканчивается позже, чем старая началась. Но проверки в
коде мало — два запроса могут пройти её одновременно. Поэтому главная защита это
уникальный индекс в самой базе на помещение и время начала. Он учитывает только
активные брони, поэтому после отмены слот снова свободен.

> 📷 **СКРИНШОТ 7** → `07-booking-409.png` — попытка занять занятый слот.

**API — 23 адреса:** `/api/auth` (3), `/api/requests` (6), `/api/facilities` (5),
`/api/bookings` (4), `/api/announcements` (5). Список заявок принимает фильтры по
статусу, категории, приоритету, комнате и поиск по тексту. Коды ответов: `200`,
`201`, `400`, `401`, `403`, `404`, `409`.

> 📷 **СКРИНШОТ 4** → `04-admin.png` — дашборд админа: счётчики, фильтры, таблица.

## 4. Docker и запуск

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
USER node
CMD ["node", "server.js"]
```

Сначала копирую только `package.json`, а потом код: Docker запоминает слои, и
пакеты переустанавливаются только когда меняются зависимости. Файл
`.dockerignore` не пускает в образ `.env`, чтобы секреты не лежали внутри.

```bash
npm install
cp .env.example .env      # вписать MONGODB_URI и JWT_SECRET
npm run seed              # демо-данные
npm start                 # http://localhost:3000
```
Через Docker: `docker build -t dormflow .`, потом
`docker run -p 3000:3000 --env-file .env dormflow`.

## Проверка и ограничения

Проверял вручную через `curl` и PowerShell: без токена → `401`, студент на
админском адресе → `403`, неправильный переход статуса → `409`, повторная бронь
того же слота → `409`.

Ограничения: проект учебный; автотестов нет; Dockerfile написал, но саму сборку
образа пока не проверял; токен живёт семь дней и не отзывается; оплата не
сделана, хотя поле цены у помещений есть.
