# DormFlow — Student Residence Management Portal

Учебный веб-проект: портал управления студенческим общежитием.
Студенты подают заявки на ремонт и бронируют общие помещения.
Администратор обрабатывает заявки, управляет помещениями и объявлениями.

Пошаговый план разработки лежит в `docs/PLAN.md`.
**Перед началом каждой новой фазы прочитай `docs/PLAN.md`** — не держи его в памяти.

## Язык

- Общайся со мной по-русски.
- Код, комментарии, интерфейс, сообщения об ошибках, тестовые данные,
  commit messages и документация — только на английском.

## Стек

- Node.js 20, менеджер пакетов **npm** (не pnpm, не yarn)
- Express.js
- MongoDB + Mongoose
- HTML, CSS, обычный JavaScript в браузере
- Порт `3000`

Не используй React, TypeScript, Vue, сборщики (Vite, Webpack), GraphQL,
WebSocket, Redis, Kubernetes — пока я не попрошу отдельно.

## Главное правило работы

За один ответ — **один маленький этап**.

Этап закончен, когда:

1. код написан;
2. сервер запускается без ошибок;
3. новая функция проверена реальной командой;
4. изменения сохранены отдельным commit;
5. commit отправлен через `git push`.

После push **остановись** и жди, пока я напишу «продолжай».
Не начинай следующий этап сам.

## Уровень кода

Пиши как обычный студент, изучающий веб-разработку: простые имена,
логичное разделение по файлам, без лишних абстракций.

Не используй dependency injection, repository pattern, сложные классы,
event systems, паттерны ради паттернов, много сторонних библиотек.

Используй Mongoose models, Express routes, controllers, middleware,
обычные HTML-страницы, CSS и `fetch` на клиенте.

Комментарии — короткие и только там, где логика неочевидна.

Я должен уметь объяснить преподавателю каждую строку.

## Как выдавать код

Ты работаешь с файлами напрямую — создавай и редактируй их сам.

- **Не выводи полный код файла в ответ.** Это шум.
- Показывай только ключевые фрагменты (5–15 строк), если без них объяснение непонятно.
- Перед изменением файла сначала прочитай его актуальную версию.
- Не переписывай работающий код, если хватает точечной правки.
- Не удаляй существующие функции без объяснения причины.
- Не используй то, чего ещё нет: модели, маршруты, переменные окружения,
  функции из будущих этапов.
- Если функция нужна на текущем этапе — реализуй её полностью, без `TODO`.

## Запуск и проверка

**Никогда не запускай блокирующие команды на переднем плане.**
`npm start` без фона повесит сессию.

```bash
npm start > /tmp/dormflow.log 2>&1 &
sleep 2
curl -s http://localhost:3000/api/health
kill %1
```

Если порт занят: `lsof -ti:3000 | xargs kill`
Если сервер не отвечает — сначала посмотри `cat /tmp/dormflow.log`.

API проверяй через `curl` и показывай реальный ответ сервера.
Postman и Thunder Client тебе недоступны, но в разделе «How to test»
оставляй для меня понятный формат:

```
Method:
URL:
Headers:
Body:
Expected result:
```

## Безопасность

- Пароли — только bcrypt hash. Пароль никогда не возвращается в API response.
- JWT secret, строка подключения MongoDB, ключи Cloudinary и Stripe — только в `.env`.
- В Git попадает `.env.example`, но **никогда** `.env`.
- Защищённые маршруты проверяют токен, административные — роль.
- Студент видит и меняет только свои записи.
- Не утверждай, что учебное приложение готово к production.

## Git

Один логический этап = один commit.

Commit message: короткий, на английском, повелительное наклонение.
Например: `Add MongoDB connection`, `Create user model`, `Fix booking date validation`.

Не объединяй этапы. Не создавай коммиты вроде `Add all backend features`.
Не создавай пустые коммиты и не подделывай даты.

Перед каждым commit:

```bash
git status
git diff
```

Добавляй файлы выборочно (`git add path/to/file`), не `git add .`,
если в папке есть несвязанные изменения. Затем проверь:

```bash
git diff --staged
```

Убедись, что в commit не попали `.env`, `node_modules` и секреты.

Если Git говорит, что изменений нет — не создавай пустой commit.
Если `push` не прошёл — покажи точный текст ошибки, объясни причину простыми
словами и **не** утверждай, что push выполнен. Не переходи к следующему этапу.
Если remote не подключён — не придумывай URL, покажи `git remote -v`.

## Формат ответа

### Current step
Одно предложение.

### What changed
Какие файлы созданы или изменены и что делает новый код. Простыми словами:
как запрос идёт от браузера к серверу, что уходит в MongoDB, что возвращает API.
Без длинных лекций. Новый метод Express, Mongoose или JavaScript объясняй одной строкой.

### How to test
Конкретные команды и ожидаемый результат.

### Commit
Commit message, список файлов, результат commit и push.

### Next step
Одно предложение. После этого остановись.

## Если я присылаю ошибку

1. Прочитай полный текст ошибки.
2. Определи вероятную причину.
3. Прочитай связанные файлы.
4. Предложи минимальное исправление.
5. Проверь, что оно работает.
6. Отдельный commit: `Fix ...`

Не смешивай bug fix с новой функцией в одном commit.
Не переписывай проект целиком из-за одной ошибки.
Не предлагай код из будущих фаз.
